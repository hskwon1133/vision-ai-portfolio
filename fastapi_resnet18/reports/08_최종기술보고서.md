# 08. 콩잎 질병 분류 Vision AI API 서비스 기술보고서

## 1. 프로젝트 정보

| 항목 | 내용 |
|---|---|
| 프로젝트 | ResNet18 기반 Beans 3클래스 분류 및 FastAPI 동기·비동기 서빙 |
| 입력 | JPG / PNG / WEBP 콩잎 이미지 (5MB 이하) |
| 출력 | `angular_leaf_spot` / `bean_rust` / `healthy` + 점수 |
| 모델 | `microsoft/resnet-18` → Head-only Fine-tuning → `artifacts/beans_resnet18` |
| 실행 구조 | Docker Compose: `web`(FastAPI) · `worker`(Celery) · `redis` · `postgres` |
| 데이터 | [AI-Lab-Makerere/beans](https://huggingface.co/datasets/AI-Lab-Makerere/beans) (train 1,034 / val 133 / test 128) |

## 2. 모델 학습 결과 요약

| 항목 | 결과 |
|---|---|
| 학습 방식 | **Head-only Fine-tuning** (Backbone 고정, `--freeze-backbone`) |
| 최종 설정 | epochs 10, lr 0.001, batch 8, seed 42 (제공 코드 수정 없이 실행 옵션만 변경) |
| 기준선 → 최종 | Validation 0.7669 → **0.9398** (+17.29%p) |
| Best Validation Accuracy | 0.9398 (125/133, epoch 6) |
| **Test Accuracy** | **0.8984 (115/128)** — 별도 평가 스크립트, 최종 모델 1회 |
| 주요 오류 | 틀린 13장 중 9장이 angular_leaf_spot ↔ bean_rust 혼동 |
| 선택 실험 | Full Fine-tuning (epochs 10): Validation best 1.0000 — 비교용, 서빙 안 함 |
| 모델 파일 | `artifacts/beans_resnet18/model.safetensors` 외 3종 |

- 데이터 점검: 손상 파일 1개 삭제, Pillow 전수 검사 손상 0, 전부 500×500 RGB, md5 중복 0건
- 모델 선택은 Validation만 사용했고 Test는 선택에 쓰지 않았다.
- 근거 문서: [산출물 1](01_FineTuning_결과보고서.md) / 원본 `artifacts/beans_resnet18/training_report.json`, `data/test_eval_beans_resnet18.txt`

## 3. 아키텍처 및 데이터 흐름

- **동기:** Browser → FastAPI → Redis Cache(DB 1) → (MISS면) ResNet18 → JSON 200
- **비동기:** Browser → FastAPI → `media/jobs/uuid.bin` 저장 + PostgreSQL(queued) → Redis Broker(DB 2) → Celery Worker → Cache/모델 → PostgreSQL(done) → 상태 조회
- web·worker는 같은 Docker 이미지, 모델은 **두 프로세스에서 각각** 로드된다.
- 근거 문서: [산출물 2](02_시스템_아키텍처.md)

## 4. API·DB 설계

- 핵심 API: `GET /health`, `POST /api/sync/classify/`(200), `POST /api/async/classify/`(202), `GET /api/async/jobs/{id}/`(200/404)
- DB: PostgreSQL `image_jobs` 1개 테이블 — 비동기 작업의 상태(`queued → running → done/failed`)와 결과. 동기 요청은 저장하지 않음. 이미지 원본은 DB가 아닌 파일로 저장.
- 실제 기록: job 1~6 모두 `done`, `failed` 미발생
- 근거 문서: [산출물 3](03_API_명세서.md) / [산출물 4](04_DB_구조_작업이력.md)

## 5. 실제 버튼 처리 검증

- 동기식: 분류가 끝난 뒤 200 응답에 결과 포함
- 비동기식: 202 + `job_id` 수신 → 1초 간격 폴링으로 `done` 확인 (job 2 화면: 접수 22ms / 전체 1,036ms)
- 동기와 비동기가 같은 캐시 함수를 써서, 동기가 저장한 결과를 비동기 Worker가 재사용함 (job 6)
- 근거 문서: [산출물 5](05_AI버튼_처리흐름.md)

## 6. 실제 성능 비교

같은 이미지, 5회 중앙값, CPU (상세 조건 → 산출물 6)

| 항목 | 중앙값 |
|---|---:|
| Sync MISS HTTP 완료 | 25.43ms |
| Sync HIT HTTP 완료 | 2.68ms |
| Async MISS HTTP 접수 | 8.57ms |
| Async MISS 최종 확인 | 63.97ms |
| 모델 추론 (Sync / Async MISS) | 19.31ms / 18.52ms |

- 비동기 접수는 동기보다 **66.30% 짧지만**, 결과 확인까지는 **38.54ms 더 길다.** 비동기는 추론을 빠르게 하는 것이 아니라 요청자가 기다리지 않게 한다.
- 동기 캐시 HIT는 MISS보다 **89.46% 짧다.** `inference_ms = null`은 추론 생략이며 0ms가 아니다.
- 콜드 스타트(컨테이너 첫 추론 약 2.15초)는 비교에서 제외하고 따로 기록했다.
- 근거 문서: [산출물 6](06_성능비교_보고서.md) / 원본 `data/timings.csv`

## 7. 기능 테스트·오류 조치

- 모의 테스트: 컨테이너에서 `python -m pytest` **4 passed**
- 실환경: 헬스, 동기 200, 비동기 202 → done, DB 기록, 캐시 MISS → HIT 확인
- 실제 오류 10건을 원인·조치·재검증으로 기록 (손상 이미지 파일, `.env` 주석 누락, 포트 점유, 템플릿 뒤바뀜, 이미지 재빌드 누락, pytest 모듈 경로 등)

## 8. 교과 9 OpenCV 성능 개선 제안 (미구현)

이번 결과에서 오류가 angular_leaf_spot ↔ bean_rust에 몰렸으므로 두 병반을 구분하는 보조 근거를 제안한다.

| 제안 | 처리 흐름 | 기대 효과 | 상태 |
|---|---|---|---|
| HSV 병반 후보 면적비 | RGB → HSV → 잎 마스크 → 황색·갈색 병반 `inRange` → Morphology → 면적비 | 병반 크기·색 분포를 수치로 기록 | 설계만, 미구현 |
| 규칙 기반 보류 | CNN `top1.score`가 낮거나(예: 0.7 미만) 병반 면적비와 예측이 엇갈리면 `확인 필요` 표시 | 오답을 확정하지 않고 사람 검토로 분리 | 설계만, 미구현 |
| CNN 점수 + OpenCV 특징 ML 보조 분류 | 클래스 점수 + HSV 통계 + Contour 개수·면적 → 보조 분류기 | 두 병해 구분 보완 | 설계만, 미구현 |
| Full Fine-tuning 모델 검토 | 실험 D 모델을 같은 Test 절차로 평가 | Validation에서 Head-only보다 높았음 | 미측정 |
| 학습률 스케줄·데이터 증강 | lr 감소 스케줄, 밝기·색·흐림·회전 증강 | lr 0.001의 val 변동 완화, 촬영 조건 강건성 | 미구현 |

- 위 제안의 임계값·효과는 검증하지 않았으며 **성능 개선 수치를 주장하지 않는다.**
- HSV 마스크는 병명을 확정하는 진단 근거가 아니다. 최종 3클래스 예측은 유지하고 보조 표시만 추가하는 방향이다.
- 검증 방법: Train으로 기준 개발 → Validation으로 비교 → 확정 후 Test 1회.
